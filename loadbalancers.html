Overview

Four Services, One Goal

Azure offers distinct load-balancing services operating at different OSI layers with different scopes and capabilities. Understanding their differences is key to building resilient architectures.

⚖️
Azure Load Balancer
OSI LAYER 4 · REGIONAL · TCP / UDP
High-performance, ultra-low-latency Layer 4 load balancing for internal and public-facing workloads within a single Azure region.
TCP/UDP Regional Millions RPS < 1ms
🛡️
Application Gateway
OSI LAYER 7 · REGIONAL · HTTP / HTTPS
Web traffic load balancer with SSL termination, URL-based routing, WAF, session affinity, and autoscaling for web applications.
HTTP/HTTPS WAF SSL Offload URL Routing
🌐
Azure Front Door
OSI LAYER 7 · GLOBAL · HTTP / HTTPS
Global CDN and HTTP load balancer with intelligent routing, WAF, DDoS protection, and anycast acceleration across Azure's edge network.
Global CDN Anycast WAF
🗺️
Traffic Manager
DNS LAYER · GLOBAL · ALL PROTOCOLS
DNS-based global traffic distributor with multiple routing methods for directing users to the optimal endpoint based on policy and health.
DNS-based Global Multi-protocol Failover

Deep Dive

Service Details

Click each service to expand a full breakdown of features, architecture, and use cases.

⚖️
Azure Load Balancer
Layer 4 · Regional · TCP/UDP · Low-latency infrastructure LB
▼
⚙️ How It Works
Azure Load Balancer operates at OSI Layer 4 (Transport). It inspects TCP/UDP packet headers — IP addresses and port numbers — and distributes traffic across backend pool VMs using a 5-tuple hash (source IP, source port, destination IP, destination port, protocol). It does NOT inspect packet payloads.
📦 SKUs
Basic — Free, up to 300 instances, no SLA, no zone redundancy. Suitable for dev/test only.

Standard — Paid, up to 1000 instances, 99.99% SLA, zone redundancy, HTTPS health probes, outbound rules, diagnostics. Required for production.
🏗️ Deployment Types
Public LB — Maps public IPs to VMs, enables outbound internet connectivity.

Internal LB — Uses private RFC-1918 IPs, routes traffic only within a VNet or on-premises — ideal for multi-tier apps (app tier → database tier).
✅ Key Features
  • 5-tuple or 2-tuple/3-tuple hash distribution
  • Health probes: TCP, HTTP, HTTPS
  • Inbound NAT rules for port-forwarding
  • Outbound rules for SNAT control
  • HA Ports — single rule covers all ports (Standard only)
  • Availability Zone redundancy (Standard only)
  • Floating IP for SQL Always On / NVA scenarios
  • Multiple frontends per single load balancer
🎯 Use Cases
VM-to-VM internal traffic SQL Always On AG Network Virtual Appliances IoT / UDP workloads Game servers SMTP/FTP backends Multi-tier app tiers
⚡ Performance
Sub-millisecond latency. No throughput cap per rule — bounded only by VM NIC limits. Supports millions of requests per second. Passes traffic in-line; no proxy hop.
🗺️ Architecture Diagram
Internet / VNet │ ▼ ┌────────────────────┐ │ Azure Load │ ← Frontend IP (Public or Private) │ Balancer (L4) │ ← Load Balancing Rules (port mapping) │ │ ← Health Probes (TCP/HTTP/HTTPS) └────────┬───────────┘ │ 5-tuple hash ┌────┴────┐ ▼ ▼ [VM 1] [VM 2] ← Backend Pool (VMs / VMSS) :22 :22 ← Inbound NAT (port-forwarding)
🛡️
Application Gateway
Layer 7 · Regional · HTTP/HTTPS/WS · Web Application Load Balancer + WAF
▼
⚙️ How It Works
Application Gateway is a managed Layer 7 reverse proxy. It terminates TLS at the gateway, inspects full HTTP request headers, URI, hostname, and cookies — then forwards to the appropriate backend pool. Operates entirely within a single Azure region.
📦 SKUs
Standard v2 — Autoscaling, zone redundancy, static VIP, header rewrite.

WAF v2 — All Standard v2 features + Web Application Firewall with OWASP 3.2 rulesets, custom rules, bot protection, rate limiting.
✅ Key Features
  • URL-based routing — /images/* → image pool, /api/* → API pool
  • Multi-site hosting — route by hostname on single gateway
  • SSL/TLS termination & end-to-end SSL re-encryption
  • Cookie-based session affinity
  • HTTP/2 support
  • WebSocket & gRPC support
  • Autoscaling (0 → 125 capacity units)
  • Header & URL rewrite rules
  • Custom error pages
  • WAF: OWASP rules, custom rules, exclusions
  • Private Link for internal backends
  • Mutual TLS (mTLS) authentication
🎯 Use Cases
Microservices routing Web app SSL offloading WAF for OWASP threats Multi-tenant SaaS hosting AKS Ingress Controller API Gateway pattern Blue/Green deployments
🏗️ Routing Types
Path-based: /api → backend-A, /static → backend-B
Multi-site: app1.contoso.com → pool-1, app2.contoso.com → pool-2
Redirect: HTTP → HTTPS, old path → new path
Rewrite: Modify request/response headers or URLs
⚡ Performance
Autoscales in minutes. Standard v2 can handle tens of thousands of concurrent connections. Latency is higher than ALB (~few ms) due to L7 inspection — acceptable for web workloads.
🗺️ Architecture Diagram
Client │ ▼ TLS Termination ┌──────────────────────────────┐ │ Application Gateway (L7) │ │ │ │ Listener → Rule → Backend │ │ [WAF inspection] │ │ [URL path map] │ └──────┬──────────────┬────────┘ │ │ /api/* /images/* ▼ ▼ [API VMs] [Image VMs] ← Backend Pools
🌐
Azure Front Door
Layer 7 · Global · HTTP/HTTPS · CDN + WAF + Intelligent Routing
▼
⚙️ How It Works
Front Door is a global anycast platform. User requests hit the nearest of Azure's 100+ PoPs (Points of Presence) worldwide. Traffic is then forwarded to backends over Azure's private WAN backbone — dramatically faster than public internet routing. TLS is terminated at the edge PoP.
📦 Tiers
Standard — CDN, static caching, custom domains, SSL offload, basic routing.

Premium — Standard + WAF managed rulesets, bot protection, Private Link to origins, security reports, sensitive data masking.
✅ Key Features
  • Global anycast with 100+ edge PoPs
  • Intelligent routing: Latency, Priority, Weighted, Session-affinity
  • Built-in CDN with caching rules
  • WAF with OWASP, bot protection, rate limiting
  • DDoS protection (L3/L4/L7)
  • TLS 1.3, HTTP/2, HTTP/3 (QUIC)
  • URL rewrite, redirect, custom headers
  • Health probes per origin group
  • Instant global failover
  • Private Link integration (Premium)
  • Real-time analytics and reports
  • Rules engine for advanced routing logic
🔀 Routing Methods
Latency: Route to lowest-latency backend (default)
Priority: Primary + failover backends
Weighted: Split % traffic across origins (A/B testing)
Session Affinity: Sticky sessions by client IP
🎯 Use Cases
Global web acceleration Multi-region active-active Static site CDN Global API Gateway DDoS mitigation Blue/Green global deploys SPA / Jamstack delivery
⚡ Performance
Anycast + Azure backbone eliminates public internet hops. Typical TTFB reduction of 30–60% vs direct origin. Cache hit = sub-10ms response from edge. TLS handshake at PoP reduces RTTs significantly for global users.
🗺️ Architecture Diagram
Users (Global) │ │ │ US EU APAC ← Anycast — nearest PoP │ │ │ └───┴───┘ │ [Front Door Edge PoP] [WAF / Cache / TLS Term] [Rules Engine] │ Azure Private Backbone │ ┌────┴──────────────┐ ▼ ▼ [US East Origin] [West Europe Origin] ← Backend origins (App Svc/AKS/LB) (App Svc/AKS/LB)
🗺️
Traffic Manager
DNS Layer · Global · Any Protocol · Policy-based DNS routing
▼
⚙️ How It Works
Traffic Manager is a pure DNS service — it does NOT proxy traffic. When a client resolves your domain, Traffic Manager returns the IP of the best endpoint based on your routing policy. Actual client traffic goes directly to that endpoint. This means it works with ANY protocol (TCP, UDP, HTTP, RDP, etc.) and any endpoint (Azure, on-prem, AWS, GCP).
🔀 Routing Methods
Performance — Lowest DNS latency region
Priority — Primary + failover (e.g., DR)
Weighted — % split across endpoints
Geographic — User's location → specific endpoint
MultiValue — Return all healthy endpoints (IPv4/IPv6)
Subnet — Map source IP ranges to endpoints
✅ Key Features
  • DNS TTL control (min 0 seconds for fast failover)
  • Endpoint health monitoring (HTTP/HTTPS/TCP)
  • Nested profiles for complex topologies
  • Multi-cloud and hybrid endpoints supported
  • Geographic compliance routing (GDPR regions)
  • Real User Measurements (RUM) for latency data
  • Traffic View analytics
  • Works with non-Azure endpoints
⚠️ Limitations
No SSL offload — just DNS
No WAF — no packet inspection
No caching — not a CDN
DNS TTL delay — failover is bounded by TTL + client cache (not truly instant)
HTTP endpoints only for health probes
🎯 Use Cases
Active-active multi-region Disaster recovery failover Non-HTTP workloads Hybrid cloud routing Geographic compliance Multi-cloud (Azure+AWS) Blue/Green DNS switch
⚡ Performance
No added latency to data path — traffic goes direct to origin. DNS resolution adds ~1–10ms one-time overhead. Failover speed depends on health probe interval (min 10s) + TTL. Set TTL to 0–30s for fast failover scenarios.
🗺️ Architecture Diagram
Client │ ▼ DNS Query: myapp.trafficmanager.net │ ▼ [Traffic Manager] ← Evaluates routing policy + health │ ├─ Performance? → Returns IP of lowest-latency endpoint ├─ Priority? → Returns primary (or failover if down) ├─ Geographic? → EU user → EU endpoint, US user → US endpoint └─ Weighted? → 70% → Endpoint-A, 30% → Endpoint-B │ Client connects directly │ [App Endpoint] (No proxy hop through TM)

Decision Guide

Which One Should You Use?

Answer these questions to quickly identify the right Azure load-balancing service for your scenario.

🌍 Scope

Is your workload within a single Azure region, or does it span multiple regions globally?
Single region → ALB or App Gateway

Multi-region HTTP → Front Door

Multi-region any protocol → Traffic Manager

🔌 Protocol

What protocol does your application use — HTTP/HTTPS, or something else like TCP, UDP, RDP, SMTP?
TCP / UDP / non-HTTP → Azure Load Balancer

HTTP / HTTPS → App Gateway or Front Door

Any protocol (DNS routing) → Traffic Manager

🛡️ Security

Do you need a Web Application Firewall (WAF) to protect against OWASP Top 10 or DDoS attacks?
Regional WAF → App Gateway WAF v2

Global WAF + DDoS → Front Door Premium

📡 CDN & Caching

Do you need to cache static content at the edge to reduce origin load and latency globally?
✓ Front Door Standard/Premium

🔁 Routing Complexity

Do you need to route traffic based on URL paths, hostnames, request headers, or geographic location?
Path/host routing (regional) → App Gateway

Path/host/geo routing (global) → Front Door

Geographic / DNS routing → Traffic Manager

🏢 Hybrid / Multi-Cloud

Do your backends include on-premises servers or resources in other cloud providers (AWS, GCP)?
Traffic Manager (any public endpoint)

Front Door (custom origins)

💸 Cost Priority

Are you optimizing for lowest cost with simple infrastructure load balancing inside a VNet?
✓ Azure Load Balancer (Standard)

⚡ Ultra-Low Latency

Do you need sub-millisecond latency (gaming, trading, real-time systems) without proxy overhead?
✓ Azure Load Balancer

Patterns

Common Architecture Combinations

These services are frequently combined to address complex enterprise requirements.

🌐 + 🛡️ Global + Regional WAF
Front Door (global CDN + anycast) in front of Application Gateway (regional WAF + path routing) in front of AKS or App Service. Two layers of WAF protection.
User → FD Edge → App Gateway → AKS
🗺️ + ⚖️ DNS + L4 Internal
Traffic Manager routes DNS to regional Azure Load Balancers. Best for non-HTTP multi-region apps needing global failover with low-latency in-region distribution.
DNS → TM → Regional ALB → VMs
🛡️ + ⚖️ L7 + L4 Tier
Application Gateway handles web tier (HTTP), Azure Load Balancer handles app/db tier (TCP). Classic two-tier architecture for multi-tier web applications.
Internet → AGW → Web VMs → ILB → DB VMs
🌐 + 🗺️ Active-Active Global
Front Door for HTTP global acceleration paired with Traffic Manager for non-HTTP or failover DNS-level control across regions and cloud providers.
HTTP → FD | TCP → TM → Regional Endpoints
